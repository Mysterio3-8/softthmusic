# SoundCloud / YouTube → VK Auto Publisher (Infinity Music)

## Автопоиск популярных треков (ТЗ 2026-08-10, сделано 2026-08-11)

Жалоба владельца: «почему в infinity music только сборники публикуются». Причина была
не в сборниках, а в треках: очередь альбомов наполнялась **только руками**
(`soundcloud_cli enqueue <url>`), ссылки кончились — и в сообществе остались одни
сборники с YouTube.

```
tg-sc-publisher.timer (каждые 3 мин)
   └─ album_publisher.tick
        pending < min_queue → sc_autofill.refill → sc_discovery.collect_new_tracks
                              каждая находка = СВОЯ строка очереди, skip_compilation=1
        альбом pending      → skip_compilation ? download_track (без сборника)
                                               : download_playlist + сборник
        альбом publishing   → пора? → один трек → next_post_at = +7..11 ч
```

| Модуль | Ответственность |
|---|---|
| `sc_discovery.py` | граница yt-dlp: поиск, отбор по популярности, ранжирование, дедуп |
| `sc_autofill.py` | добор очереди до нормы |

**Чем ищем и почему (проверено живыми вызовами 2026-08-11):**

- `scsearch<N>:<запрос>` отдаёт `view_count`/`like_count` уже во flat-режиме — то есть
  популярность видна ДО скачивания, одним дешёвым запросом;
- 🔴 **официальные чарты SoundCloud не читаются**: `soundcloud.com/discover/sets/
  charts-top:all-music:ru` даёт HTTP 404 у `soundcloud:set` (в этой версии yt-dlp
  отдельного экстрактора чартов нет). Ставить чарты в `sources` бесполезно;
- ссылка вида `https://api.soundcloud.com/tracks/soundcloud%3Atracks%3A<id>` (именно её
  отдаёт поиск) скачивается напрямую — резолвить страницу трека не нужно.

**Порядок выдачи — релевантность, а не популярность.** В одном ответе на «русский рэп
2026» рядом стояли трек на 12 млн прослушиваний и трек на 748. Отсюда `min_plays`
(порог) и сортировка — без них «популярные треки» были бы просто случайными.

«Желательно русские» реализовано как **предпочтение, а не фильтр**: русские идут первыми,
внутри группы — по прослушиваниям. Выбрасывать хит на 10 млн из-за латиницы хуже, чем
поставить его вторым.

**Дедуп двойной** — по ссылке И по паре «исполнитель — название»: один хит лежит на
SoundCloud десятками перезаливов с разными id, и без второго ключа очередь набивалась бы
копиями одного трека.

**`skip_compilation`** (новая колонка `albums`, самолечащаяся миграция): находка
автопоиска — это ОДИН трек, и сборник из него опубликовал бы то же аудио дважды.
Плейлисты, поставленные руками, работают как раньше — сборник, затем треки.
⚠️ Момент публикации такого трека считается от ПОСЛЕДНЕГО трека в сообществе
(`post_log`), а не от начала альбома: у каждой находки свой альбом из одного трека, и
отсчёт от начала выпустил бы два трека подряд.

Выключается одной строкой `soundcloud.discovery.enabled: false` — тогда поведение ровно
прежнее, ручное.

## Сборники плейлистов с YouTube (ТЗ владельца 2026-08-10) — ТРЕТИЙ поток

Готовые ПОЛЬЗОВАТЕЛЬСКИЕ плейлисты с YouTube / YouTube Music качаются потреково,
склеиваются в один ролик, публикуются в VK, а файл отдаётся владельцу для заливки
на YouTube руками.

```
tg-yt-playlists.timer (каждые 15 мин)
   └─ app/yt_playlists_cli.py tick → yt_playlists.tick
        очередь пуста → sync: discover_playlists по источникам
        пора?         → download_playlist → render (подпись 10 сек на каждом треке)
                      → concat → vk.upload_video + post_now
                      → deliver: ready/ + Telegram (если ≤50 МБ)
```

| Модуль | Ответственность |
|---|---|
| `yt_source.py` | граница yt-dlp: поиск плейлистов, скачивание треков + обложек |
| `yt_playlist_db.py` | очередь плейлистов. Единственное место с её SQL |
| `yt_playlists.py` | оркестрация тика, тексты записи и описания |
| `overlay.py` | подпись «исполнитель — трек» (Pillow → PNG → ffmpeg overlay) |
| `delivery.py` | отдача готового файла владельцу (`ready/` + Telegram) |
| `yt_playlists_cli.py` | sync / tick / status |

**Чем лучше сборников Минусов:** там `playlists.py` берёт ЧУЖОЙ готовый ролик
целиком и подменяет фон. Здесь сборник собирается из отдельных треков — отсюда
честные тайминги, подпись на каждом треке и своя обложка; чужой видеоряд не
переиспользуется вообще.

**Объёмы (ТЗ 2026-08-11: «надо 2 трека и 2 сборника»):** 2 трека
(`soundcloud.max_posts_per_day`, интервал 420–660 мин) + 2 сборника
(`youtube_playlists.max_posts_per_day`, интервал 420–620 мин). Счётчики РАЗДЕЛЬНЫЕ —
`post_log.kind`, `AlbumQueue.posts_since(kinds=...)`; иначе потоки съедали бы квоту
друг друга.

**Названия сборников** (жалоба 2026-08-11: «у плейлистов одинаковые название одни и те
же», «надо более кликабельные, больше байта, без цензуры можно добавить»). Было две
причины, а не одна:

1. 🔴 **защита от повторов не работала вообще.** `recent_titles` читала колонку `title`,
   а там лежит название плейлиста-ДОНОРА — наше свежесобранное название не могло
   совпасть с ним никогда. Добавлена колонка `published_title` (миграция), `mark_published`
   её заполняет.
2. Шаблонов было восемь и все безликие. Теперь в шаблоне есть `{artists}` — исполнители
   ИЗ САМОГО сборника. Это и байт, и SEO, и естественная уникальность: одинаковый набор
   первых трёх артистов дважды подряд почти не встречается.

Шаблоны без `{artists}` остаются запасом на случай, когда исполнителей не разобрали.

**Поиск плейлистов.** Источником может быть ссылка на плейлист ИЛИ произвольный
текст — тогда это поисковый запрос по ПЛЕЙЛИСТАМ
(`youtube.com/results?...&sp=EgIQAw%3D%3D`). Обычный `ytsearch` не годится: он ищет
одиночные ролики.

**Подпись на видео.** Первые 10 секунд каждого трека поверх кадра висит
«название + исполнитель» (`overlay.py`, `media.build_caption_filter`). Кадр —
размытая копия обложки во весь экран + чёткий оригинал по центру.
⚠️ Нужны **Pillow** и шрифт `assets/fonts/DejaVuSans-Bold.ttf` (доставляется
`deploy.sh`, в `requirements.txt` добавлен). Нет шрифта → подпись молча
пропускается, рендер не падает.

**Отдача файла.** Bot API режет отдачу на 50 МБ, а сборник из 15 треков весит
больше. Поэтому файл кладётся в `ready/` и живёт `ready_keep_days` дней, а в
Telegram уходит либо сам файл (если влез), либо готовая команда `scp`. Заливать на
YouTube автоматически нельзя — OAuth-кредов до сих пор нет.

**Грабля ffmpeg:** в команде есть `-map` для звука, а значит автоматический
маппинг выключен — выход filter_complex ОБЯЗАН иметь явную метку `[v]`, иначе
видео просто не попадёт в файл (`media.build_filter_graph`).

## SEO (ТЗ 2026-08-10)

Запись короткая, **описание видеозаписи большое** — это разные индексируемые поля
VK, и в ленте описание свёрнуто. В описание уходят поисковые фразы, блок про сервис
и полный набор тегов; ссылка на бота в нём — та самая внешняя ссылка, ради которой
всё затевалось (страницы VK индексируются Google и Яндексом).

Настраивается в `soundcloud.post`: `base_tags`, `search_phrases`, `channel_phrases`,
`post_tag_limit`, `video_tag_limit`, `service_block`. **Пока они пусты — оформление ровно
прежнее** (`post_builder.seo_configured`). Общая картина — `all_auto/SEO.md`.

⚠️ **`search_phrases` и `channel_phrases` — разные сорта ключей, путать нельзя.**
Первые — шаблоны с `{q}` вокруг артиста и релиза, работают только когда артист известен.
Вторые — постоянные запросы САМОГО сообщества («музыка без цензуры», «инфинити музыка»,
ТЗ 2026-08-11). По теме ищут на порядок чаще, чем по имени артиста, и такой запрос не
зависит от того, разобрались ли метаданные — поэтому идут в КАЖДОЙ публикации.

# SoundCloud → VK Auto Publisher

**Статус:** 🟢 альбомный поток в проде, сквозной прогон пройден 2026-07-29 на
«ARGUMENTS & FACTS» (Big Baby Tape): 5 треков скачаны, склеены, сборник в отложке VK.
YouTube-поток выключен (`yt-vk-publisher.timer` disabled). 71 тест зелёный. Каталог на VPS: `/opt/yt-vk-publisher`, в реестре бота — `p_minus`.

## Что это

Два независимых потока в одном проекте, публикуют в группу VK 240295467 «Free Music»:

1. **YouTube → VK** (исходный, `main.py`) — берёт ролики из плейлистов YouTube Music.
   **Выключен насовсем** решением владельца 2026-07-28: таймер `yt-vk-publisher.timer`
   отключается, код и тесты оставлены рабочими.
2. **SoundCloud → VK** (`soundcloud_cli.py`) — кидаешь боту ссылку на плейлист, он
   скачивает треки с обложками, склеивает в один сборник, публикует его, а дальше
   выкладывает треки по одному раз в 3–5 часов. Как закончит — пишет в Telegram.

## Архитектура альбомного потока

```
бот Новостей (📦 Софты → 🎵 Загрузить плейлист)
   └─ subprocess ─▶ soundcloud_cli.py enqueue <url>  → строка в albums (pending)
tg-sc-publisher.timer (каждые 3 мин)
   └─ soundcloud_cli.py tick → album_publisher.tick
        альбом pending    → soundcloud.download_playlist → media.render/concat
                          → vk.upload_video + schedule_post → status=publishing
        альбом publishing → пора? не ночь? → один трек → next_post_at = +3..5 ч
        треки кончились   → status=done → notifier.send «готово»
```

Момент следующей публикации лежит в БД (`albums.next_post_at`), а не в расписании
systemd. Таймер только спрашивает «пора?» — поэтому случайный интервал переживает
рестарт сервера, и нет двух источников правды о времени.

| Модуль | Ответственность |
|---|---|
| `album_db.py` | очередь: albums / album_tracks / post_log. Единственное место с их SQL |
| `soundcloud.py` | граница yt-dlp: плейлист → треки + обложки, дедуп обложек по хешу |
| `media.py` | граница ffmpeg: обложка+аудио → mp4, concat склейка |
| `album_scheduler.py` | чистая логика: случайный интервал + ночное окно |
| `album_publisher.py` | оркестрация тика |
| `notifier.py` | Telegram sendMessage (без поллинга) |
| `soundcloud_cli.py` | enqueue / tick / status |

`vk_client.py`, `publisher.py`, `youtube.py`, `database.py` — YouTube-поток, альбомным
не затронуты.

## Токены VK (важно — анти-бан)

Два токена по назначению, чтобы не палить user-токен частым постингом:
- `VK_GROUP_TOKEN` (группа 240295467) — `wall.post` (отложенные записи).
- `VK_USER_TOKEN` (админ, scope `video`) — ТОЛЬКО `video.save`. VK не даёт грузить
  видео групповым токеном: проверено вживую 2026-07-18 — `video.save` групповым
  токеном → **`[5] User authorization failed`**.

Видео грузится В ГРУППУ (`video.save(group_id=...)`) → владелец вложения сообщество,
поэтому групповой токен корректно прикрепляет `video-GID_ID` к записи.

## Антибан альбомного потока

| Параметр | Значение | Где |
|---|---|---|
| Ночная пауза | **выключена** (`0`/`0`) — решение владельца 2026-07-29 | `soundcloud.quiet_*_hour` |
| Интервал | случайный **240–330** мин | `soundcloud.*_interval_minutes` |
| Предохранитель | **5 постов/сутки** | `soundcloud.max_posts_per_day` |
| Возобновление утром | +0..45 мин джиттера (не работает без паузы) | `album_scheduler` |

**Арифметика режима.** 1440 мин / 5 постов = 288 мин — это ПОТОЛОК среднего интервала.
240–330 даёт среднее 285 и ровно ~5 постов, то есть лимит и интервал сошлись: сутки
закрываются полностью, растянуто. Хотите интервал больше — уменьшайте число постов,
иначе никак: 10 постов в сутки уже требуют среднего 144 мин.
Значения снижены 2026-08-05 по ТЗ владельца после бана второго личного токена
(«остался один, беречь его, растянуть на 24 часа»). Было 12 постов и 95–140 мин.

Альбом на 20 треков расходится примерно за 3 дня. Суточный счётчик считает ВСЕ записи
(сборник + треки) по таблице `post_log`, а не по трекам — иначе сборник проходил бы
мимо лимита.

⚠️ Круглосуточный постинг противоречит общему антибан-правилу семьи проектов
(`all_auto/CLAUDE.md`: ночная пауза 6–8 ч). Включено сознательно по требованию
владельца. Вернуть паузу — поставить `quiet_start_hour: 23`, `quiet_end_hour: 9`.

## Оформление поста

```
🎧 Big Baby Tape — ARGUMENTS & FACTS (Album) | Без цензуры

00:00 1. FAX                                  ← только у сборника
01:55 2. Surname

♾️ Слушать в Telegram бесплатно и без цензуры: <listen_url>
#big_baby_tape_arguments_facts                ← уникален для трека И для альбома
```

Этот же текст идёт **описанием под видео** и **названием видео** (первая строка).
Строка «📢 Канал» появляется, только если задан `channel_url` — сейчас он пуст.

Всё настраивается в `soundcloud.post` без правки кода. Два момента:

- **`flag` ставится руками.** Страны артиста в метаданных SoundCloud нет — вывести
  её автоматически неоткуда. Меняй под релиз или держи нейтральный эмодзи.
- **`hashtag_template`** решает уникальность: `{artist}_{name}` даёт свой тег каждому
  треку (20 треков = 20 тегов), `{artist}` — один общий на исполнителя.
  `hashtag_group` — короткое имя сообщества VK. У группы 240295467 своего короткого
  имени нет (screen_name = club240295467), поэтому поле пустое и тег идёт без «@».
  Задашь имя в настройках VK — впиши его сюда.

## Инварианты

- Секреты только в `.env`, никогда в config.yaml/коде.
- Постинг — групповым токеном; user-токен — только загрузка видео.
- Публикация НЕМЕДЛЕННАЯ (`wall.post` без `publish_date`) — решение владельца
  2026-07-29. Отсюда шаг таймера 3 мин: минута записи = минута тика, при шаге 15
  мин все посты падали бы на одни и те же 4 значения минут.
- Один альбом в работе за раз. Новая ссылка встаёт в очередь, не вклинивается.
- После публикации трека его файлы удаляются; каталог альбома сносится на финише.

## Грабли

- `VkUpload.video(..., wallpost=0)` — именно `0` (int), не `False`: vk_api сериализует
  Python `False` в строку `"False"`, VK её не парсит (урок «Новостей»).
- yt-dlp нужен ffmpeg в PATH — и для извлечения mp3, и для склейки. На VPS 6.1.1, есть.
- Шаблоны названий (`{name} — {artist} | {suffix}`) чистят осиротевшие разделители:
  трек без автора даёт «Track | без цензуры», а не «Track —  | без цензуры».
- Обложка копируется каждому треку в свой файл: треки публикуются днями и подчищают
  файлы за собой — общий файл оставил бы соседа без арта.
- Приватные и «секретные» ссылки SoundCloud не поддержаны (нужна авторизация).
- 🔴 **yt-dlp сам не может обновить `client_id` — и это роняло ВСЁ скачивание.**
  Ключ он добывает только с главной `soundcloud.com/`, а она отдаёт этому серверу
  **403**. При этом страницы артистов и треков открываются (200) — то есть IP чистый,
  блокируется именно главная. Без ключа падает КАЖДЫЙ трек, альбом помечается
  «Ни один трек не скачался». Так молча провалились ВСЕ альбомы с 30.07 по 06.08
  (id 21–26): очередь выглядела пустой, владелец видел «музыки нет».
  Лечится `soundcloud.ensure_client_id()` — тянет ключ из JS-бандлов страницы, которую
  сервер открыть может, и кладёт в кеш yt-dlp. Самолечение бесплатное: на 401/403
  yt-dlp сам обнуляет кеш, следующий вызов добудет свежий.
  **Диагностировать так:** `curl -o /dev/null -w "%{http_code}" https://soundcloud.com/`
  (403) против страницы трека (200). Если обе 403 — тогда уже IP.
- **Часть треков SoundCloud отдаёт под DRM** (`This video is DRM protected`) — такие
  пропускаются, это не поломка. У одного артиста часть треков качается, часть нет.
- **`MAX_TRACKS_PER_ALBUM = 30`.** Ссылка `/tracks` у плодовитого артиста отдаёт сотни
  треков (kizaru — 358), а тик качает плейлист ЦЕЛИКОМ, рендерит видео на каждый трек
  и склеивает в ОДИН сборник. 358 треков = ~20 часов видео и несколько ГБ на 1 ядре и
  8 ГБ свободного диска. Нужно продолжение — ставь ту же ссылку в очередь повторно.
- **Время — МСК явно в коде (`album_scheduler.MOSCOW`), не из TZ процесса.** Юнит
  стоит с `TZ=Europe/Moscow`, а тот же CLI руками по SSH получит UTC сервера:
  наивное время разъезжалось на 3 часа. Наивное на входе трактуется как МСК.

  приводить к UTC (`_to_utc_iso`), иначе «+03:00» и «+00:00» сравниваются по цифрам.
- **Ночная пауза проверяется до ветвления тика**, а не только на треках: сборник —
  такая же запись в сообществе, ночью палит бота ровно так же.
- `wall.get` и `wall.edit` групповым токеном НЕ работают (`[27] Group authorization
  failed`) — читать и править записи можно только user-токеном.
- `extract_flat: True` у SoundCloud не отдаёт названия и длительности треков (только
  id). Для превью и треклиста нужен обычный `extract_info` без flat.
- Точные ретраи +1ч/+3ч YouTube-потока работают только в `--schedule`; в `--once`
  ролик с ошибкой берётся заново на следующем суточном прогоне.

### SEO-движок сборников (`seo_engine.py`, ТЗ 2026-08-18)

Заголовок, описание и ключи собираются ИЗ ПАРАМЕТРОВ сборника, а не берутся из списка
готовых строк: жанр, год, число треков, настоящие артисты, настроение, ситуация.
Тридцать конструкций плюс словарь жанров дают тысячи непохожих названий и растут от
правки СЛОВАРЯ, а не кода — двести статичных строк кончились бы на двухсотом сборнике.

Три правила движка, на каждое есть тест:

1. **не врать** — артист попадает в заголовок только из треклиста, число треков только
   настоящее (заказ на 12 треков не станет «100 лучших»);
2. **не спамить** — «РЭП 2026 РУССКИЙ РЭП ЛУЧШИЙ РЭП…» отбраковывается по повтору слова
   и длине (`looks_spammy`, потолок 100 знаков);
3. **не повторяться** — конструкция, дающая уже выходившее название, не берётся
   (`recent_titles`).

⚠️ **Падежи держатся данными, а не кодом.** У каждого жанра в базе есть `genitive`
(«русского рэпа»), и конструкции вида «Лучшие треки {genre_gen}» участвуют только там,
где он задан. Без этого выходило «Лучшие треки русский рэп». Добавляешь жанр в базу —
добавь падеж, иначе часть конструкций для него просто отключится.

Настроение и ситуация выбираются жребием из словаря жанра, иначе все сборники выходили
бы «для машины». Ключи — база жанра плюс длинный хвост с годом, ситуацией и артистами.

Выключается строкой `youtube_playlists.seo_engine: false` → возвращаются прежние
`title_templates`.

## Checkpoint (2026-08-18 — кнопка «сборник по жанру», чистка треклиста, окно на день)

**Кнопка «🎼 Сборник по жанру»** в боте (📦 Софты → карточка Музыки). Нажатие кладёт в
очередь сборников строку с меткой `заказ` (`SOURCE_REQUEST`), тик берёт её ПЕРВОЙ —
вперёд своей подборки и вперёд чужих плейлистов YouTube. Не нажали — поток работает
как раньше, жанр выбирается случайно.

| Правило заказа | Значение | Почему |
|---|---|---|
| Квота | занимает слот из двух суточных | нагрузка на единственный VK-аккаунт не растёт |
| Порог популярности | `min_plays=0` | решение владельца: узкий жанр выше 100k может не набраться |
| Минимум треков | 3 (`REQUEST_MIN_TRACKS`) | короткий сборник лучше, чем нажатая впустую кнопка |
| Заказов в очереди | максимум 2 (`MAX_PENDING_REQUESTS`) | третий всё равно ждал бы следующей ночи |
| Отчёт | только при ошибке | файл и так приходит в Telegram |

✏️ Править жанры пишет их в `manager_contract.yaml`, и контракт перекрывает `config.yaml`
ЦЕЛИКОМ (удалённый в боте жанр обязан исчезнуть с кнопки). Контракта нет → работает
config, ровно как раньше. Живой конфиг не версионируется — правка руками на сервере
теряется, поэтому путь через контракт основной.

**🔴 Треклист сборника собирался из СЫРЫХ метаданных.** `download_track` отдаёт
`artist = uploader` (паблик-перезаливщик) и полное название ролика, а разобранная пара
всё это время лежала рядом в `TrackRef` и не использовалась. Отсюда живой сборник
[285](https://vk.com/wall-240295467_285): «New Russian Rap Music — Батальон Морской
Пехоты», «⊹ — ВАЙБ 2025», «**** — icarus. - Русский Фонк». Теперь имена берутся
разобранные, плюс гейт (`track_naming.usable_track`, `has_artist_separator`):

* нет разделителя «артист — песня» → трек не берём (иначе артистом станет паблик);
* имя без букв («****», «⊹») → мимо;
* название или артист — ЯРЛЫК подборки → мимо. Ярлык считается по ДОЛЕ служебных слов
  (строго больше половины), а не по «все слова служебные»: живая строка «русский реп

  Ровно половина оставлена честным названиям («Русский вальс», «Танцы минус»).

Отсев может не набрать минимума — тогда сборник честно не собирается. Запас поиска
поднят вдвое → втрое.

## Checkpoint (2026-08-17 — сборники ожили: четыре причины простоя, а не одна)

Сборников не было с 14.08. Владелец видел одно: «сборники не приходят». Причин оказалось
ЧЕТЫРЕ, и каждая маскировала следующую — починив одну, я получал ту же тишину.

1. 🔴 **Состав плейлистов.** Поиск по «chill плейлист на русском» приносит не песни, а
   подборки ЧАСОВЫХ диджей-миксов: живой замер — 3514, 3435, 3659 с на «трек». 13 таких =
   4 ГБ аудио и 13 часов видео; рендер шёл дольше двух часов, systemd убивал юнит по
   `TimeoutStartSec` ровно на склейке, следующий тик начинал заново. **Ни одной ошибки в
   журнале** — с точки зрения кода ничего не падало. Лечение: гейт по ПЛОСКОМУ списку до
   скачивания (`max_track_seconds` 900, `max_total_seconds` 7200, `min_tracks` 5) и новый
   статус `rejected` — состав от повторов не меняется, и `revive_failed` возвращал бы
   миксы вечно.
2. 🔴 **CDN отдавал `403` на самих данных** при исправных метаданных: выход отдавал 5
   аудиоформатов и при этом ронял каждый трек. Проверять выход запросом метаданных
   БЕСПОЛЕЗНО — он ответит «жив». Переключаемся по ПУСТОМУ результату скачивания
   (`proxy_candidates`, `YT_PROXY_PORTS`). Живой лог: `Скачано треков: 15 … (выход
   socks5://127.0.0.1:10813)` после 403 на основном.
3. 🔴 **`deploy.sh` перезапускал только таймер треков.** Копировал ОБА юнита, делал
   `daemon-reload`, а `restart` — одному. 16.08 таймер сборников остался `inactive` и
   простоял 22 часа: очередь полна (66 плейлистов), юнит `enabled`, в журнале софта
   тишина, потому что его просто никто не запускал.
4. 🔴 **Гонка тиков.** Тик идёт 25–30 мин, таймер ходит каждые 15 — в один рабочий
   каталог писали ТРИ процесса. Пока сегменты назывались финальными именами, они просто
   перезаписывали друг друга; после перехода на атомарную запись `finally` одного стал
   удалять временный файл другого → `ffmpeg: Unable to re-open output file for shifting
   data`. Лечение — `single_run.py`, замок на файле с протуханием через 3 часа
   (`finally` при SIGKILL не выполняется, а именно так процесс умирает от OOM).
